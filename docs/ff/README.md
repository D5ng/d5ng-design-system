## 읽는 방법

- **원문 요지**는 원문이 제시한 문제와 개선 방향을 요약해요. 긴 문장이나 전체 예제는 옮기지 않았어요.
- **Before·After**는 원문 사례의 구조를 짧게 재구성한 코드예요. import와 주변 선언은 생략했어요. 폼처럼 두 방식 모두 유효한 사례는 우열 대신 선택 조건을 적었어요.
- **적용하지 않는 경우·다른 항목과의 상충**은 별도 표시가 없으면 이 문서의 판단 가이드예요. 원문이 직접 설명한 예외에는 이를 표시했어요.
- **React 컴포넌트 props API에 적용**은 이 저장소 맥락으로 확장한 해석이에요. 예시 타입과 컴포넌트는 API 선택지를 설명하며, 현재 패키지가 제공하는 API라는 뜻은 아니에요.
- R·P·C·K 번호는 이 문서의 탐색용 번호예요. 공식 규칙 번호나 기계적인 합격 기준이 아니에요.

## API를 판단할 때의 경계

FF는 변경 비용을 비교하는 기준이지 특정 prop 철자를 정하는 명세가 아니에요.

- P2는 **같은 종류의 함수의 반환 형태**를 다뤄요. 서로 다른 상태인 `disabled`·`loading`이 반드시 boolean이어야 한다는 증명은 아니에요. boolean과 enum의 선택은 독립성·배타성·플랫폼 관례로 별도 판단해요.
- P1을 근거로 `state`라는 prop 자체를 금지할 수는 없어요. React의 state와 단어가 같다는 사실보다, 그 컴포넌트에서 어떤 동작을 약속하는지가 중요해요.
- Figma의 시각 상태 목록과 React의 제어 API는 같지 않을 수 있어요. 브라우저의 hover·active·focus 상태와 애플리케이션이 제어하는 loading을 구분하는 건 상태 소유권에 관한 설계 판단이에요.
- `loading`이 클릭을 막는지는 별도의 동작 계약이에요. 이름에 더해 타입 문서·스토리·테스트로 명시해야 해요. 주석만 썼다고 모든 숨은 로직 문제가 해결되는 건 아니에요.

원문 총론도 네 기준 사이의 긴장을 설명해요. 함께 바뀌어야 할 규칙은 묶고, 독립적으로 바뀔 흐름은 나누되, 실제 변경 시나리오로 판단해요.
